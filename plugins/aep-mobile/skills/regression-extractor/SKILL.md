# Mobile Regression Extractor

## Purpose
Bridges the test generation pipeline and the BrowserStack Test Management database. It executes during the pre-build ingest phase of the `sdet-plan-generator` to query and retrieve currently documented active regression cases, ensuring that newly authored test plans never duplicate existing coverage.

---

## Input Contracts

Receives search metadata extracted from the core contexts:
* **`app_id`**: The target app (e.g., `gojek-driver`, `gojek-consumer`).
* **`feature_key`**: The specific feature being planned (e.g., `OneKYC`).
* **`module_namespace`**: The active sub-system/module (e.g., `Onboarding`).

---

## Execution Workflow

### 0. Reading the checked-in corpus — never load a file whole
Files under `${CLAUDE_PLUGIN_ROOT}/config/` are generated by
`scripts/regression_corpus/build_corpus.py` (a CI job on each source repo,
not something this skill runs itself) and give the module→project resolution
and repo-derived navigation **without needing a local clone of any repo.**
This plugin draws on **three** automation repos, each with its own module
vocabulary: `gmt` (gojek-mobile-tests, the original/primary source), `gtf`
(gtf-mobile-tests, GoPay-focused: gopay-consumer-app, gopay-merchant-app,
gopay-kyc-mob-web), and `tapmind` (tapmind-mobile-tests, an NLP framework
covering the two merchant apps gmt has no coverage for). Read
`config/browserstack_project_map.json` (~5 KB) directly — it's small.

**`config/deeplinks.json` and `config/nav_index/<repo>/<module>.json`
(some modules exceed 3 MB — `nav_index/gmt/driverapp.json` alone is ~3.5 MB,
roughly 900,000 tokens as plain text) must NEVER be opened with the Read
tool.** Reading one of the larger files whole would consume most or all of
the context window on a single lookup. Instead, shell out for a **targeted**
extraction of just the module/id you need, e.g.:
```
python3 -c "import json; d=json.load(open('${CLAUDE_PLUGIN_ROOT}/config/nav_index/<repo>/<module>.json')); print(json.dumps(d['cases'].get('<case_number>')))"
```
This costs the same handful of tokens (just the matched record) no matter
how large the file is on disk. Same rule for `deeplinks.json` — it is
repo-namespaced (`{"repos": {"gmt": {"modules": {...}}, "gtf": {"modules": {...}}}}`),
so target `json.load(...)['repos']['<repo>']['modules'].get('<module>')` for
the one repo+module in scope, never the whole file. TapMind's nav_index is a
third sibling under the same `nav_index/` root (`nav_index/tapmind/<module>.json`),
alongside `nav_index/gmt/` and `nav_index/gtf/`; its module→project map lives
right alongside those files, at `config/nav_index/tapmind/project_map.json`
(no `deeplinks.json` equivalent) — see the TapMind join step below.

### 1. Match Project and Execute BrowserStack Query (via MCP)
- **Step 1a — resolve `app_id` to its module set FIRST, across all repos that cover it.** `app_id` (e.g. `gojek-consumer`, `gopay-consumer`) is a different vocabulary from any repo's own module names — they are not 1:1. Read `config/browserstack_project_map.json`'s **`app_id_to_modules`**: each entry has a `modules` array (gmt) and optionally sibling `gtf_modules` / `tapmind_modules` arrays — an app_id can be covered by more than one repo at once, and all present arrays must be resolved and queried, not just the first one found.
  - `gojek-consumer` → 10 gmt modules (9 share `PR-176`; `gopay` is an 11th-app-binary module — same app, package `com.gojek.app` — filed under its own project, query it separately from PR-176).
  - `gojek-driver` → `driverapp` + `driver-platforms` + `driver-platform-android` (gmt only, same app, TestRail project 122, split across three repo modules — query all three, not just one).
  - `gopay-consumer` → gmt's `gopay-consumer` module (standalone GoPay app, package `com.gojek.gopay`) **AND** gtf's `gopay-consumer-app` module (`gtf_modules`, same app's staging/nightly build variants) — query both, tag results by repo+module. Do **not** use the `gopay` module for this app id — that module's package matches `gojek-consumer`, not `gopay-consumer`, despite the similar name.
  - **`gofood-merchant` and `gopay-merchant` → `modules: []` in gmt (confirmed NO_COVERAGE there, and gtf independently confirms the same zero-coverage result for gofood-merchant), but NOT a bare stop-and-return.** Both have a `tapmind_modules` entry (`gofoodmerchantapp` project 174, `gopaymerchant` project 168) that IS queryable — TapMind is the primary automation source for these two app_ids, resolved via the TapMind join step below, not via `browserstack_project_map.json`'s own `separate_projects`/`gtf_source`. `gopay-merchant` additionally has a `gtf_modules: ["gopay-merchant-app"]` entry: real case ids exist there (5, via Cucumber `@C<digits>` tags) but no project id is recorded anywhere in gtf for them, so treat that source as informational only (flag with `WORTH_CHECKING`, do not query BrowserStack for it) until a PIC confirms a project id. Only emit `extraction_status: LIMITED` + stop-before-querying for these two app_ids if the TapMind join (below) *also* comes back empty — that is the actual "nothing anywhere" case, not gmt's `NO_COVERAGE` alone.
- **Step 1b — resolve each gmt/gtf module to its BrowserStack project**, using the module sets from 1a:
  - gmt: if the module is one of `consumer_super_app.folders`' keys, the project is **`consumer_super_app.browserstack_project`** (e.g. `PR-176`) and the folder id(s) come from that module's entry — no project search needed. If it's `driverapp`/`driver-platforms`/`driver-platform-android` (human-confirmed to share the same BrowserStack project ids), there is no single static project: resolve **per case** via the live Lumos resolver noted in the map (`resolution` field); `static_fallback_pr_id` is the last-resort fallback the repo itself uses. `gopay` resolves to **`PR-173`** (human-confirmed). Otherwise look it up in `separate_projects`.
  - gtf: look the module up in **`gtf_source.separate_projects`** (same shape as gmt's `separate_projects` — `browserstack_project`, `testrail_ids`, `source_files`, sometimes a `note`). None of gtf's project ids are BrowserStack-confirmed yet as of this corpus generation.
  - Either repo: if the resolved entry has a non-null `browserstack_project`, use it. If `browserstack_project: null`, the id genuinely isn't confirmed yet — do not guess or search all projects; raise a `NEEDS_ANSWER` note naming the repo+module and ask for the project id, then proceed with what's available from the other repo(s)/TapMind if any.
- Establish connection to the **BrowserStack MCP Server** (relying on client-configured OAuth or credentials) only to fetch the live test-case inventory for the *resolved* project(s) — not to discover which project it is. Any app_id resolving to more than one project/module (across one or more repos) — query each and merge the results, tagging each `regression_tests[]` entry with the repo+module it came from.
- **Fetch Folder Hierarchy (Optional):** If a `module_namespace` is provided and its folder id isn't already known from the map, query `listFolders` to find it.
- **Fetch Test Cases:** Invoke the **`listTestCases`** tool with the resolved `project_identifier` (and folder ID if resolved), passing the extracted `feature_key` and `module_namespace` as filters/tags.
- **Join to the repo for navigation and step quality.** For each returned case, strip the `C` prefix to get `case_number`, look it up in `config/nav_index/<repo>/<module>.json` (targeted lookup — see Step 0; `<repo>` is `gmt` or `gtf`, matching whichever repo resolved this module in 1a/1b). A match gives accurate `steps`/`navigation` from the repo; no match means the case is manual-only or not yet automated — keep BrowserStack's own steps and flag weak ones.
- **Join to the TapMind corpus for automation steps (third source repo).** `tapmind-mobile-tests` is the NLP-framework automation repo; its checked-in nav_index is `config/nav_index/tapmind/` — a third sibling directory alongside `nav_index/gmt/` and `nav_index/gtf/` (namespaced per-repo, since its module names — `driverapp`, `gofood`, … — collide with gojek-mobile-tests). Its module→project map lives alongside those files, at `config/nav_index/tapmind/project_map.json`. For each returned case, look its `case_number` up in `config/nav_index/tapmind/<module>.json` with a **targeted** shell read (same rule as Step 0 — never load the file whole):
  ```
  python3 -c "import json; d=json.load(open('${CLAUDE_PLUGIN_ROOT}/config/nav_index/tapmind/<module>.json')); print(json.dumps(d['cases'].get('<case_number>')))"
  ```
  A match gives the case's real, repo-verified TapMind step sequence (`tapmind_steps`: ordered `{kind, text}` — `login`/`toggle`/`deeplink`/`network`/`nlp`); copy it **verbatim** into that `regression_tests[]` entry's `tapmind_steps`. This is what the sdet-plan-generator reuses as a scenario's `automation_steps`. No match → omit `tapmind_steps` (many cases have a GMT/Cucumber test but no TapMind port yet — that is normal, never invent one). Note: TapMind also covers **merchant apps** (`gopaymerchant`, `gofoodmerchantapp`) that gmt has as `NO_COVERAGE` — for those app_ids, the TapMind corpus is the primary automation source, so still run this join (querying TapMind's own project ids 168/174 via BrowserStack) even when gmt's project map returned `NO_COVERAGE` and regardless of what gtf's `gtf_modules` entry (if any) turned up.
- **Extract the module's deeplink dictionary (targeted, never the whole file).** The repo deeplink dictionary is the pipeline's PRIMARY navigation source — the downstream `sdet-plan-generator` uses it at rung 1 of its Navigation Resolution Ladder to reach a *new-feature* screen with a single `Open deeplink` step, before falling through to fragile UI walks. Surface it so the generator can. For each resolved repo+module in scope, shell out for just that module's entries (per Step 0's rule — do **not** Read `deeplinks.json` whole):
  ```
  python3 -c "import json; d=json.load(open('${CLAUDE_PLUGIN_ROOT}/config/deeplinks.json')); m=d['repos'].get('<repo>',{}).get('modules',{}).get('<module>',{}); print(json.dumps({k:(v.get('android') or v.get('raw')) for k,v in m.items()}))"
  ```
  Copy the result verbatim into `deeplink_dictionary` keyed by module (`{ "<module>": { "SCREEN_NAME": "<uri>" } }`) — when the same app_id resolves modules from both gmt and gtf, include both modules' dictionaries, keyed separately (do not merge two modules' entries under one key). Flatten each entry to its usable URI (`android`, else `raw`); never edit, complete, or invent a path. Include **all** of the module's entries, not only those matching existing cases — the generator needs the full dictionary to resolve *new* screens the feature introduces (e.g. a benefits page reached by `LOYALTY_REWARDS`) that no existing case covers. Omit `deeplink_dictionary` entirely if `deeplinks.json` is unreadable, and raise a `WORTH_CHECKING` note — never emit an empty object, which reads as "this module has no deeplinks".

### 2. Format Output (`regression_context.json`)
Output conforms to `${CLAUDE_PLUGIN_ROOT}/schemas/regression_context.schema.json`. The payload
carries `extraction_status` (`COMPLETE` / `PARTIAL` / `LIMITED`) and `extraction_notes[]`
(`{ field, reason, action, follow_up }`) alongside the results — same contract as every other
skill in the pipeline. `COMPLETE` only when the query actually ran and `extraction_notes` is empty.

Each retrieved case object (`regression_tests[]`) must include:
* **`id`**: BrowserStack case identifier verbatim (e.g., `C2879733`).
* **`case_number`**: the numeric case id without the `C` prefix — the join key to the repo's `@TestInfo`/`@GBTTestRail` `testCaseIds` and Cucumber Examples. BrowserStack is the system of record; this number was carried over from TestRail during migration (project id is mapped to BrowserStack in each module's result-listener, e.g. `CucumberExecutionListener` / `lumosClient.getProjectIdFromTestCaseId`).
* **`title`**: The exact title of the existing test case.
* **`status`**: Current state in BrowserStack (e.g., `Active`, `Draft`). Include only Active normally.
* **`priority`**: Severity tier (`P0`, `P1`, `P2`) as reported by BrowserStack.
* **`case_type`**: e.g. `Regression`, `Functional`.
* **`is_automated`**: Boolean — `true` when an automated counterpart exists (matched by `case_number`).
* **`scope`**: `own_module` (the feature's own module) or `impacted_area` (pulled in via `rfc.affected_modules`).
* **`source_module`**: the repo module this case came through (e.g. `gopay`, `gofood`, `driverapp`). Required whenever `app_id` resolves to more than one module (see Step 1a) — without it, a `gojek-consumer` result set spanning 10 modules is unreadable.
* **`steps`** + **`steps_source`**: execution steps, preferring the repo's accurate steps when an automated counterpart exists (`steps_source: repo`); otherwise BrowserStack's own steps as-is (`steps_source: browserstack`), which may be weak/empty — flag those in `extraction_notes`.
* **`preconditions`**: Extracted environment or configuration requirements.
* **`navigation`** + **`nav_source`**: ordered steps to REACH the screen (distinct from the case's own steps), resolved via the navigation ladder — `deeplink` → `existing_test` → `figma` → `needs_answer`. A `needs_answer` nav_source is recorded and flagged, never guessed.
* **`tapmind_steps`**: the case's real TapMind automation sequence from `config/nav_index/tapmind/<module>.json` (ordered `{kind, text}`), copied verbatim, when a TapMind test exists for this case_number — per the TapMind join step above. Omitted when none exists. Feeds the generator's `automation_steps`.
* **`variant_dimensions`**: the case's own BrowserStack **custom fields** that partition the tested population, copied verbatim as `{ field_name: [values] }` — e.g. `{"DriverType": ["IDBike","IDCar"], "Country v2": ["Indonesia"]}`. `listTestCases` already returns these in each case's `custom_fields[]`; carry them through instead of dropping them. **App-agnostic — never hardcode which fields these are:** copy whatever custom fields the project defines (a driver app's `DriverType`/service-type fields, a consumer app's payment-instrument or user-tier fields), skipping only the ones already mapped to first-class columns (`Execution Mode`, `Platform`, automation-status fields). Keys and values are passed through exactly as BrowserStack reports them — never normalised, translated, or extended with a value no case declared. This is the pipeline's **only observed enumeration of which variants real coverage actually splits on**, and the sdet-plan-generator depends on it to fan out test-data fixtures per variant rather than inventing a value or silently omitting the dimension. Absent custom fields → omit the field for that case (do not emit `{}`).

Also set the run-level fields: `app`, `feature_key`, `module_namespace` (feature's own + impacted), `browserstack_project` (e.g. `PR-176`, resolved from the module→project map, never guessed), `resolved_folders` (the folders actually searched), and `deeplink_dictionary` (the resolved module(s)' deeplink entries from `config/deeplinks.json`, per the extraction step above — the generator's rung-1 navigation source).

Finally set **`observed_variant_dimensions`** — the per-key union of every case's `variant_dimensions` in this run (e.g. two cases tagged `IDBike` and one tagged `IDBike`+`IDCar` → `{"DriverType": ["IDBike","IDCar"]}`). It is a roll-up of what was actually returned, never a catalogue of what the app theoretically supports: a value appears here only because some returned case declared it. Omit the field entirely when no case carried custom fields — an empty object would wrongly read downstream as "checked, and this app genuinely has no variants".

### 3. Validate — report, never block
```
python3 -c "import json,jsonschema; jsonschema.validate(
  json.load(open('regression_context.json')),
  json.load(open('${CLAUDE_PLUGIN_ROOT}/schemas/regression_context.schema.json')))"
```
Passes → write it. Fails → still write it, convert each validator error into an `extraction_notes`
entry (`follow_up: NEEDS_ANSWER`) and set `extraction_status: PARTIAL`. Validator unavailable →
write it with a `WORTH_CHECKING` note on `ENVIRONMENT`; never report an unvalidated output as valid.

## Guardrails
- **No Hallucinations:** Only return test cases actually returned by the BrowserStack MCP tool. Never invent, complete, or "reconstruct" a test case, ID, title or step list.
- **Distinguish zero results from no answer.** A query that ran and matched nothing → `[]` with `extraction_status: COMPLETE`. A query that could not run → `[]` **plus** `extraction_status: LIMITED` and a `NEEDS_ANSWER` note on `ENVIRONMENT`. Never emit a bare `[]` for a failed lookup: downstream that reads as "no existing coverage" and the SDET plan duplicates the entire existing suite.
- **Connection failure → continue, flagged.** If the BrowserStack MCP server is unreachable or unauthorised, return `[]` with a `NEEDS_ANSWER` note: reason *"BrowserStack MCP unavailable — regression coverage was NOT checked"*, action *"configure the BrowserStack MCP server and re-run, or dedup manually"*.
- **Project mapping failure → continue, flagged.** If a module cannot be resolved to a project via `config/browserstack_project_map.json` (not present in `consumer_super_app.folders`, `separate_projects`, or `gtf_source.separate_projects`, or present with `browserstack_project: null`), return `[]` for that module with a `NEEDS_ANSWER` note naming the repo+module and stating the map has no confirmed project id for it — but still resolve and query the app_id's *other* modules/repos (see Step 1a) rather than failing the whole run. Never guess a `PR-` id and never search all BrowserStack projects to find one.
- **Never read `deeplinks.json` or a `nav_index/<repo>/<module>.json` file whole.** Always extract the single repo+module/case_number needed via a shell one-liner (Step 0). Some `nav_index` files exceed 3 MB; reading one directly can consume the entire context window for a single lookup.
- **Secure Credentials:** Never attempt to prompt for, read, or print BrowserStack API tokens. All authorization is handled securely at the client-mcp level.
